# 面试问答：这个项目怎么讲

配套文档：[技术链路说明](技术链路说明.md)。

## 0. 先定调：这是一个“可运行的 PoC”

诚实定位比夸大更加分：

- 已经跑通：解析 → 分块 → 向量化 → 混合检索 → 图谱抽取 → 带引用问答；
- 数据规模小：5 篇文档、77 个块、367 个实体、1018 条关系；
- 没做量化评估：目前是人工抽查，没有 Recall / nDCG 数字；
- 没上生产：单机、全量重建、无权限、无监控。

面试里主动说清边界，反而显得可信。

## 1. 30 秒版本（自我介绍里用）

> 我做了一个本地可运行的文档知识库。它把 Word 和 PDF 解析成带标题层级的文本块，用 text-embedding-v3 生成 1024 维向量存进 Milvus；同时用大模型从块里抽实体和关系存进 Neo4j。查询时向量召回和 BM25 关键词召回各取 Top10，用 RRF 融合取 Top6，再把命中段落和图谱的一跳关系交给大模型，生成带 `[n]` 引用的回答。前端是 FastAPI 加一个单页，能直接看两路召回命中和图谱。目前 5 篇文档、77 个块，建库大约 31 秒。

## 2. 2 分钟版本（项目深挖开场）

按“问题 → 方案 → 取舍 → 验证 → 不足”讲：

1. **问题**：政策文档既有“学费多少”这种语义问题，也有“APS”“GB/T 20801.1”这种精确词；只用向量会漏专有名词，只用关键词会漏同义表达。
2. **解析**：PDF 用 MinerU 的 pipeline 后端保留版面、表格、阅读顺序；DOCX 用 python-docx 保留标题和表格顺序。
3. **分块**：标题优先切，单块上限 650 字、80 字重叠，块头拼上“文档 + 章节”，让向量和 BM25 都带上下文。
4. **存储**：Milvus 一个 collection 同时存 1024 维稠密向量和 BM25 稀疏向量；稀疏向量由 Milvus 的 BM25 Function 自动生成，中文分词用内置 chinese analyzer。
5. **融合**：两路各 Top10，RRF k=60 融合取 Top6。选 RRF 是因为两路分数量纲不同，按排名融合不用调权重。
6. **图谱**：按块用 DeepSeek 抽实体关系，白名单约束类型，`name::type` 去重，写 Neo4j；检索时把命中块的实体做 1 跳扩展，作为结构化上下文。
7. **验证**：4 组查询人工检查召回，浏览器端检查三个页面；量化评估还没做，方案是构造 30-50 条带标准块的问题，算 Recall@5、MRR、nDCG 和引用准确率。
8. **不足**：没有 reranker、没有增量更新、图谱有噪声、语料太小。

## 3. 高频问题与回答模板

### Q1：为什么选 Milvus？和 FAISS、Elasticsearch、pgvector 比呢？

**回答：**

> 我需要三样东西同时成立：稠密向量、BM25 稀疏向量、元数据过滤，而且希望是一个数据库而不是自己拼。Milvus 2.6 原生支持 BM25 Function 和 hybrid search，RRF 直接内置；FAISS 只是向量索引库，没有 BM25、过滤和增删管理；Elasticsearch 的关键词能力强，但稠密向量和混合排序不是它的主场；pgvector 上手快，但稀疏检索和大规模向量性能弱一些。代价是 Milvus 要额外维护 etcd 和 MinIO，组件比 pgvector 重。

**可能的追问：数据量这么小，用 Milvus 是不是过度设计？**

> 是有一点。这个小数据量用 SQLite + FAISS 也能跑。我选 Milvus 主要是想把“混合检索 + 过滤 + 扩容”的链路走通，作为方案验证；如果只是几十篇文档的固定知识库，确实可以更轻。

### Q2：为什么要混合检索？BM25 和向量各自解决什么？

> 向量解决“语义相近但字面不同”，比如“费用”能召回“学费开销”；BM25 解决“字面必须命中”，比如“APS”“11,904 欧元”“GB/T 20801.1”。政策文档里专有名词和数字很多，单靠向量容易把“APS 审核”召回成“签证材料”。两路召回后融合，能同时覆盖两类需求。

### Q3：RRF 是什么？k=60 怎么来的？为什么不用加权求和？

> RRF 按排名算分：`score = Σ 1/(k + rank)`，k 默认 60。两路都排第 1 的块得 `2/61≈0.0328`，只在单路排第 5 得 `1/65≈0.0154`，所以双路命中的块会靠前。不用加权求和是因为向量分数在 0~1，BM25 可能到 30，量纲不同，要先归一化再调权重，调参成本高；RRF 只看排名，天然可比。代价是丢掉了分数差距的信息，如果两路质量差异很大，RRF 不如调好的加权。

**追问：k 的作用？**

> k 越大，排名差异被压得越平；k 越小，头部排名权重越大。60 是文献里的常用默认值，我没做 k 的消融，这是可以补的实验。

### Q4：分块为什么是 650 字、80 重叠？是固定长度吗？

> 不是固定长度，是“标题优先 + 长度上限”。遇到标题先切，正文累积到 650 字左右再切，切的时候优先找句号、分号、换行，避免句子被切一半；相邻块保留 80 字重叠。650 是按中文政策文本一段的常见长度定的，块太大检索粒度粗，太小上下文不足。实测 77 个块平均 348 字、中位数 304，因为很多块在标题处提前切了。

**追问：怎么证明 650 是最优？**

> 没有证明，这是经验值。正确做法是固定测试集，比较 300/500/650/800 几档的 Recall@5 和答案质量，我现在没做这个消融。

### Q5：Embedding 怎么做的？为什么用 text-embedding-v3？

> 每个 chunk 单独调 text-embedding-v3，1024 维，每批 10 条，因为接口单次最多 10 条；换行和空串做清洗，失败重试 3 次。选它是因为中文效果稳定、按量付费、不用在本机部署模型。代价是依赖网络和外部服务，离线场景不合适。如果换模型，维度变化必须重建 collection，不同模型的向量也不能混用。

### Q6：为什么不用本地 BGE-M3？GPU 不是空着吗？

> 当时的主要考虑是少维护一套模型环境和显存占用，先用 API 把链路跑通。BGE-M3 的好处是 dense、sparse、多语言一体，还能省掉 BM25 服务端分词；如果要做离线或降成本，我会换 BGE-M3，并用同一批测试集比较效果。

### Q7：知识图谱的 schema 怎么定的？

> 先看数据里反复出现什么。留学政策里稳定出现的是国家、州、院校、项目、学位、考试、费用、签证、要求、奖学金、机构，所以定了 11 类实体；关系只保留能支撑查询的 9 种，比如 LOCATED_IN、OFFERS、REQUIRES、CHARGES。图谱结构是 Document→Chunk→Entity，实体之间再挂关系。这样既能从文档追溯到原文块，也能做实体间跳转。

**追问：为什么不用通用本体（比如 Schema.org）？**

> 通用本体覆盖太广，落到这个垂直场景会产生大量用不上的类型，抽取时反而更容易乱。垂直场景用小而窄的本体，约束更强、噪声更低。

### Q8：LLM 抽取实体关系，怎么防幻觉？

> 四层：Prompt 明确“只抽文中明确出现的信息”；实体类型和关系类型双重白名单；关系两端的名字必须在本次抽出的实体列表里；temperature 设 0。抽不出来或调用失败就退回规则抽取。即便这样，367 个实体里仍有少量泛化词和错误合并，所以生产上还要加人工抽检、别名词典和置信度过滤。

**追问：怎么评估抽取质量？**

> 现在没做系统评估。可行的是人工标 100 个块的三元组，算实体 Precision/Recall 和关系准确率；再用下游问答的提升来间接验证。这个我还没做，是下一步。

### Q9：图谱在检索里具体怎么用？为什么不直接用图谱回答？

> 检索还是以 chunk 为主：先混合检索拿 Top6，再用这些块的 chunk_id 找它们提到的实体，取实体的一跳关系，最多 30 条，拼进 Prompt 作为结构化补充。不直接用图谱回答，是因为图谱只覆盖抽出来的显式关系，大量细节还在原文里；图谱适合补充“谁属于谁、谁要求谁”，不适合替代原文。

### Q10：什么数据适合建知识图谱？GB/T 为什么不适合？

> 适合的是实体边界清楚、关系反复出现、需要多跳查询的数据，比如院校—地区—专业—要求，或者产品—厂商—兼容性。GB/T 20801.1 是条款型标准，主体是“3.2 术语”“4 设计条件”这种层级条款，强行抽只会得到“管道”“压力”这类无区分度的节点，所以只建 Document→Chunk，不抽实体。检索仍然能用向量和 BM25 命中条款。

### Q11：MinerU 用的什么模型？用 VLM 了吗？

> 用的是 MinerU 2.6.5 的 pipeline 后端，没有用 VLM，也没有下载 VLM 模型。pipeline 里包含 DocLayout-YOLO 做版面、YOLO v8 做公式检测、UniMERNet 做公式识别、PaddleOCR 做 OCR、layoutreader 做阅读顺序，模型合计约 3.3GB。VLM 更适合扫描件、手写、复杂图表，但 4.x 的 VLM 后端要本地 parse-server 或 vLLM，Windows 上不稳，所以先用 pipeline。

**追问：那 PDF 里的表格和公式怎么办？**

> pipeline 本身有表格分类/结构识别和公式识别，这次 PDF 以文字条款为主，主要收益是版面块和阅读顺序。如果是复杂表格，还可以把表格单独转成 Markdown/HTML 再入库。

### Q12：MinerU 4 不是更新吗，为什么退回 2.6.5？

> 4.0.12 改成了客户端/服务端模式，CLI 必须先起本地 parse-server，默认还没有可用引擎；而且它会往用户目录写文档库锁文件。2.6.5 的 `-p/-o/-b pipeline` 一条命令就能跑，模型也能指定到项目目录，稳定性更适合这个环境。这是工程取舍，不是 4.x 不好。

### Q13：一次查询的完整链路？延迟瓶颈在哪？

> 查询先做 embedding（网络 200-400ms），然后 Milvus 稠密和 BM25 各 Top10（十几毫秒），RRF 融合（同一次请求内），Neo4j 查一跳关系（十几毫秒），最后 DeepSeek 生成（2-5 秒）。瓶颈明显在大模型生成，其次才是 embedding 网络调用。要优化就做流式输出、缓存高频问题、把 embedding 换成本地模型。

### Q14：检索效果怎么评估？现在 Recall 多少？

> 目前没有量化指标，只做了 4 组人工抽查：德国学费、APS 材料与周期、新加坡硕士条件、GB/T 适用范围，前 4 条都能命中相关文档。量化方案是构造 30-50 条问题并标注标准块，算 Recall@5、MRR、nDCG@10，再做 dense / BM25 / hybrid / hybrid+图谱 的消融。这个还没跑，我不会编数字。

> 如果面试官继续追问，可以补一句：以现在 77 个块的规模，Recall@5 很容易做得很好看，参考意义有限；真正有价值的是扩到几千块后再测。

### Q15：数据量涨到百万块怎么办？

> 分三层：存储上 Milvus 可以分片、加副本；索引上从内存型换成 IVF/HNSW 或 DiskANN；工程上做增量入库、异步 embedding、按 doc_id 删除、缓存热点查询。BM25 的稀疏索引也会随规模变大，需要评估内存和延迟，必要时把关键词通道换成独立搜索引擎。这些是设计推演，我没有在百万级验证过。

### Q16：新增、删除、修改文档怎么做？

> 现在是全量重建：`ingest.py` 会先删 collection 和清空图谱，再重新解析、向量化、抽取。新增文档能跑，但成本随语料线性增长。生产做法是：以 doc_id + 内容哈希做版本，新增只插入，修改先按 doc_id 删除旧块再插入，删除同时清 Milvus 和 Neo4j；解析和 embedding 放到任务队列。

### Q17：权限隔离怎么做？

> 当前没有权限。思路是把 tenant_id / acl 作为标量字段写进 Milvus，检索时用 expr 过滤；Neo4j 里给 Document/Chunk 加租户属性，查询时先按租户裁剪；API 层从 token 取租户，不信任前端传参。图谱的实体是否跨租户共享要单独设计，不能简单复用。

### Q18：为什么不用 GraphRAG / LightRAG？

> GraphRAG 的核心是社区发现 + 社区摘要，适合“全局性问题”，比如“这批文档的主要趋势是什么”；代价是建库成本高、更新麻烦。我的场景更多是具体条款和院校信息，chunk 检索 + 一跳图谱已经够，属于按需取用。语料只有 5 篇，做社区摘要收益不明显。如果扩到几百篇并出现全局总结需求，我会再评估 GraphRAG。

### Q19：这个项目最大的难点是什么？

> 不是调通某个 API，而是让各段的语义对得上：解析出来的标题层级要能指导分块，分块的上下文要能同时被向量和 BM25 利用，图谱实体要能挂回块。中间踩了两个典型坑：Milvus 2.6 的 BM25 必须查稀疏字段而不是文本字段，否则报 1100；MinerU 4 的 CLI 改成了服务端模式，直接跑会提示没有可用引擎。都是先看错误、再查引擎语义解决的。

### Q20：如果重做，你会改什么？

> 三件事：第一，先建 30-50 条评估集再调参，不然分块和 TopK 都是拍脑袋；第二，加 reranker，向量 + BM25 召回 Top20 后精排；第三，把全量重建改成按 doc_id 增量更新。另外会把图谱抽取的产物落一份 JSON 方便人工审，而不是直接写库。

### Q21：成本大概多少？

> 现在只有 embedding 和大模型调用。embedding 是 77 个块、8 次请求，成本可以忽略；图谱抽取 60 次 DeepSeek 调用；问答每次一次调用。具体金额取决于单价和 token 量，我没有精确账单。工程上能省的是缓存 embedding、减少重复抽取、把高频问题答案缓存。

### Q22：安全上要注意什么？

> 三类：Prompt 注入——文档内容可能包含“忽略以上指令”，要在系统提示里声明资料只是资料，并且不把资料当指令执行；Cypher 注入——关系类型是白名单拼接，不能直接用模型输出拼查询；密钥——现在 `.env` 明文，生产要放密钥管理，并且不能把 `.env` 提交到仓库。

## 4. 讲“难点”的 STAR 模板

面试官爱听“你怎么解决问题”，可以选一个讲：

### 案例 A：BM25 查询报 1100

- **S**：混合检索第一版把 BM25 查询打在 `text` 字段上。
- **T**：需要让关键词通道和向量通道都能召回。
- **A**：报错是 `field (text) to search is not of vector data type`。查 Milvus 2.6 的 BM25 语义后确认：查询要打在 `sparse_vector` 字段，`data` 仍传原始文本，服务端用同一个 analyzer 生成查询稀疏向量；改字段后通过。
- **R**：双路召回正常，RRF 融合生效。
- **L**：不能只看客户端 API 形状，要理解引擎侧的字段语义。

### 案例 B：MinerU 4 跑不起来

- **S**：装完 MinerU 4.0.12，`parse` 提示“本地 mineru 服务未运行”。
- **T**：要在 Windows 上稳定解析 PDF。
- **A**：起本地 server 后仍提示“没有 basic/standard/advanced 引擎”；同时它往用户目录写文档库锁文件，被环境拦截。评估后回退到 2.6.5 的 pipeline 模式，把模型缓存、YOLO 配置、matplotlib 缓存全部重定向到项目目录。
- **R**：PDF 一次解析成功，8 页 111 个 block。
- **L**：新版本不一定更适合当前平台，稳定性和可运维性也是选型标准。

## 6. 被问住时的万能答法

不要硬编。用这个结构：

> “这块我目前没做 / 没测。我的判断是……；如果要补，我会先……，验证口径是……。”

例子：

> “百万级我没压测过。我的判断是瓶颈会从 embedding 转到索引内存和 BM25 延迟；如果要补，我会先做 10 万块的压测，记录 P95 延迟和内存，再决定换 DiskANN 还是分片。”

## 7. 不要说的几句话

- ❌ “用了 GraphRAG” —— 实际是 chunk 检索 + 一跳图谱，不是社区摘要。
- ❌ “用了 VLM 解析 PDF” —— 实际是 pipeline，VLM 模型都没下载。
- ❌ “Recall 提升了 30%” —— 没有量化评估，不能编数字。
- ❌ “千万级没问题” —— 没压测过。
- ❌ “RRF 就是加权融合” —— RRF 是按排名，不是按分数加权。
- ❌ “BM25 是语义检索” —— BM25 是词频/逆文档频率的关键词匹配。
- ❌ “知识图谱什么数据都能建” —— 条款型、叙述型数据收益很低。

## 8. 现场演示建议

网络不稳时不要现场跑大模型，提前准备好：

1. 检索页：查“APS 审核周期多久”，展示 D/B 徽标和 RRF 分数；
2. 图谱页：查“海德堡大学”，展示院校—州关系；
3. 问答页：查“新加坡硕士申请条件”，展示引用和“用到的图谱关系”。

如果面试官问“为什么这条排第一”，就打开结果原文，指出它同时被 D 和 B 命中，RRF 得分更高。
